# 功能展示說明｜作品集 Demo 腳本

**使用對象**：面試官、門市管理者、測試人員。這是一份**操作引導與建議展示順序**，不是新的功能清單。前端文字保留使用者已驗收版本，不在文件階段修改畫面。

## Demo 前準備（推薦測試資料）

- 啟動 MySQL 與 Spring Boot，確認 `/login` 可開啟；備有可登入的測試帳號（不在簡報或 Git 中公開密碼）。
- 建立第一層「飲料」及第二層「茶類」，建立如「紅茶」「綠茶」兩項有效商品，設定庫存、售價及安全庫存。
- 建立兩家有效供應商，為上述商品設定可供貨關聯與採購價。
- 準備可用的中央氣象署 Key，並選擇未來 7 天內的日期；天氣資料會變動，不要把 `1.04` 當作固定預期值。
- 準備一個庫存不足情境（例如庫存 3 件，銷售 5 件）供錯誤處理展示。
- Demo 建議使用測試資料庫，避免實際營運資料被展示操作修改。

## 兩段可以在面試時說的故事

### 1. 為什麼不是只憑最高溫度補貨？

系統逐日取 `1.00 + temperatureAdjustment + humidityAdjustment + rainAdjustment`，再算區間平均。若某七天中一天倍率為 `1.00`、六天為 `1.05`，則平均為 `7.30 / 7 ≈ 1.04`。這是**冷飲銷售的規則式假設**，使用者可從說明視窗看到每天如何計算，也能手動選擇是否套用天氣。

### 2. 一次賣多種商品，為何不是一次寫一筆？

目前資料庫每項商品都要獨立記錄，以支援不同商品的庫存及部分退貨；同一次交易用 `batch_id` 關聯。失敗時使用 `@Transactional` 回滾批次，成功時同一批共用銷售時間。未來如果需要付款、會員、收銀員，才考慮正式新增銷售主檔。

## 異常流程建議驗收

1. **庫存不足**：同批有一項不足，確認全部未扣庫存也未新增銷售。
2. **退貨**：退一項商品 1 件，只回補該商品；超過剩餘退貨量／7 天期限會遭拒絕。
3. **採購狀態**：同張單重複送出／重複確認到貨，正常序列操作會被狀態限制拒絕；**併發重複到貨仍列為部署前專案審查事項**。
4. **跨台灣日期**：昨日的 DRAFT 不可直接送出，保留資料可查看。
5. **登入權限**：未登入讀取 `/api/products` 會收到 `401`，修改密碼後需重新登入。
6. **外部天氣異常**：測試預報不完整時警告與中性處理，不可把 `null` 呈現為 0% 機率。

## Demo 時應避免的描述

- 不要說「所有商品都適用冷飲天氣倍率」或「這是機器學習預測」；目前屬於規則式、可解釋的商業假設。
- 不要說「已支援多節點高可用」；目前是單一執行個體，Session Registry 位於記憶體。
- 不要說「已接 AWS／Docker／GitHub Actions」；那是下一個部署階段。
- 不要說「資料庫只有六張表」；目前有九張實體表。
- 不要在公開簡報或錄影展示 `.env`、CWA 授權碼、MySQL 密碼、管理員密碼。
